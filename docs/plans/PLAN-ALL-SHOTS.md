# PLAN-ALL-SHOTS — экран «Все выстрелы»

## 1. Цель

Новый read-only экран: общая мишень со всеми выстрелами спортсмена из всех его
тренировок, с глобальной сквозной нумерацией. Кнопка входа — рядом с кнопкой
«Замечания» на экране `TrainingsScreen`.

## 2. Требования (из задачи)

- Кнопка «Все выстрелы» рядом с «Замечания».
- Общая мишень со всеми выстрелами спортсмена из всех тренировок.
- Глобальная нумерация 1..N (сквозная, не per-training `shotNumber`).
- Координаты — исходные (`shot.x`/`shot.y` как есть, без пересчёта/смещения
  между тренировками).
- Выстрелы с замечаниями — синие.
- Клик по выстрелу выбирает его и показывает номер/оценку внизу — как в
  обычной установке (аналог `displayScore` в `TrainingScreen`).
- Комментарий показывается через tooltip.
- Zoom-кнопки работают (full / 7-10 / 9-10, как в `TrainingScreen`).
- `TargetCanvas` в read-only режиме: нельзя добавлять/перемещать выстрелы.
- Без фильтров (по дате/тренировке и т.п.) — весь набор сразу.

## 3. Дизайн-решения, требующие фиксации

### 3.1. Что входит в «все выстрелы»

Только выстрелы со `status === 'committed'`. Черновики (`draft`) — переходное
состояние активной сессии `TrainingScreen`, в сводном read-only экране не
показываются.

### 3.2. Порядок и правило глобальной нумерации

Тренировки сортируются по `startedAt` (по возрастанию), внутри тренировки —
по `shotNumber` (по возрастанию, уже монотонный). Глобальный номер = позиция
в этой объединённой последовательности (1..N). При равенстве `startedAt`
(не ожидается в проде, но для детерминизма теста) — вторичная сортировка по
`training.id`.

**Решение после oracle review:** `shot.shotNumber` в БД остаётся per-training
и не переписывается и не мигрирует — `globalNumber` существует только как
производное значение в `AllShotsEntry`, вычисляемое `listAllShotsForAthlete`
на лету при каждом открытии экрана. Он не сохраняется в `ShotRecord`, не
участвует в сортировке/выборе `lastShot` в `TrainingScreen` и не влияет на
остальной код — это чисто аналитический артефакт для `AllShotsScreen`.

### 3.3. Цвет «с замечанием» vs выделение кликом

В `TrainingScreen` синий (`#3B82F6`) уже означает «выбранный» выстрел, зелёный
— «последний/перетаскиваемый». В новом экране синий требуется для «есть
замечание», а клик должен что-то показывать внизу, но по заданию не обязан
менять заливку маркера. Решение: заливка маркера определяется только
наличием комментария (чёрная по умолчанию, синяя `#3B82F6` при наличии
комментария); выбор кликом не меняет заливку, а подсвечивается увеличением
маркера до его "emphasis"-размера (`getShotMarkerDims(zoomMode, true)`),
как уже используется для last/dragging — без изменения смысла существующих
размерных констант. Это не требует новых цветовых констант и минимально
раздвигает `TargetCanvas`.

### 3.3.1. Подпись номера на маркере (100+)

Маркер выстрела на мишени физически мал; трёх/более-значный номер на нём
нечитаем и может визуально ломать разметку. Решение: подпись на маркере
(`shotLabels`) показывается только для `globalNumber` в диапазоне 1..99;
для `globalNumber >= 100` подпись на маркере не рендерится вовсе (маркер без
числа, как выстрелы без подписи вообще). Полный номер без ограничения
всегда показывается в нижней панели при выборе выстрела (см. §4.5, формат
`№{globalNumber} • {score}`) — ограничение касается только надписи на самом
маркере, не нижней панели.

### 3.4. Tooltip с комментарием

Нативный SVG `<title>` внутри `<g>` маркера выстрела, если у выстрела есть
хотя бы один комментарий (текст первого/единственного комментария —
конвенция уже принята в `RemarksScreen`, где на выстрел ожидается 0 или 1
комментарий через `existingCommentId`). Ограничение: нативный `<title>`
показывается по hover на desktop; на touch-устройствах browsers это не
гарантированно всплывает — известный риск, фиксируется в разделе 6.

### 3.5. Zoom persist

Экран переиспользует тот же setting-ключ `targetZoomMode` (общий с
`TrainingScreen`), чтобы масштаб был согласован между экранами — как уже
принято для этого ключа в `db/settings.ts`.

## 4. Изменяемые/новые файлы

### 4.1. `src/domain/allShotsRepo.ts` (новый)

```ts
export interface AllShotsEntry {
  shot: ShotRecord;
  globalNumber: number; // 1..N, chronological across trainings
  hasComment: boolean;
  commentText: string | null; // first comment text, for tooltip
}

export async function listAllShotsForAthlete(athleteId: string): Promise<AllShotsEntry[]>
```

Реализация: `listTrainings(athleteId)` (внимание: возвращает тренировки в
порядке `startedAt` DESC — это текущий порядок для списка тренировок в UI,
а не хронологический) → явно пересортировать копию массива по `startedAt`
ASC (вторично по `id` ASC для детерминизма при равенстве) → для каждой
тренировки в этом ASC-порядке `listShots(training.id)`,
отфильтровать `status === 'committed'`, конкатенировать в порядке §3.2 →
пронумеровать 1..N → `listCommentsByAthlete(athleteId)` → построить
`Map<shotId, CommentRecord>` (первый по `createdAt`) для `hasComment`/
`commentText`.

### 4.3. `src/components/TargetCanvas.tsx` (правка)

Добавить опциональные props, без изменения поведения по умолчанию:
```ts
readOnly?: boolean;                 // default false
onSelectShot?: (shotId: string) => void;
commentedShotIds?: Set<string>;     // shots to render in blue
shotTooltip?: (shotId: string) => string | null; // text for <title>
shotLabels?: Map<string, number>;   // shotId -> label number to render on marker
                                     // (globalNumber for AllShotsScreen); if absent,
                                     // existing default label behaviour is unchanged
```

**Решение после oracle review (номер на маркере):** `TargetCanvas` не знает
о понятии `globalNumber` и не вычисляет его — он получает готовый
`shotLabels: Map<shotId, number>` отдельным пропом и просто рендерит
переданное число на маркере, если карта передана и содержит id выстрела.
Это сохраняет `TargetCanvas` переиспользуемым и без знания о per-training vs
глобальной нумерации; `AllShotsScreen` строит `shotLabels` из
`entries.map(e => [e.shot.id, e.globalNumber])`, а `TrainingScreen`
продолжает не передавать этот проп (текущее поведение подписи маркера, если
оно есть, не меняется).
- `onDragStart`/`onDragMove`/`onDragEnd`/`onDragCancel` становятся
  опциональными (`?:`), т.к. read-only режим их не использует.
- В `handlePointerDown`: если `readOnly`, искать `findNearestShot` и, если
  найден, вызвать `onSelectShot(shot.id)`; при промахе — ничего не делать
  (никакого `onDragStart` для нового выстрела). Не вызывать
  `setPointerCapture`/не начинать drag-цикл.
- `handlePointerMove`/`handlePointerUp`/`handlePointerCancel`: no-op при
  `readOnly` (эффективно недостижимы, т.к. drag не стартовал, но добавить
  ранний `if (readOnly) return;` для явности и защиты от чужого кода).
- Заливка маркера: `fillColor = commentedShotIds?.has(shot.id) ? '#3B82F6' : (existing logic)`.
  В read-only режиме "existing logic" (isDragging/isLast/isSelected) не
  применяется вовсе — `isSelected`/`isLast` вычисляются только не-readOnly;
  emphasis для readOnly определяется отдельно через `selectedShotId` (уже
  существующий prop) — маркер увеличивается (`emphasis = isSelected`), но
  цвет не зависит от выбора.
- Лупа (`TargetLoupe`) не рендерится в read-only (нет `dragScreenPoint`,
  т.к. `dragging` всегда `null`) — уже так по существующей логике, изменений
  не требует.
- `<title>{tooltipText}</title>` добавляется первым child в `<g>` маркера,
  если `shotTooltip?.(shot.id)` вернул непустую строку.

### 4.4. `src/components/targetCanvasReadOnly.test.tsx` (новый)

**Стратегия тестирования readOnly/pointer после oracle review.** Текущий стек:
`vitest.config.ts` не задаёт `test.environment` (дефолт `node`, без DOM), в
проекте нет `@testing-library/*` и не установлен `jsdom`/`happy-dom`;
существующие `*.render.test.tsx` рендерят через `renderToStaticMarkup` и не
создают реальных `PointerEvent`. Добавлять `jsdom`/`happy-dom` и
`@testing-library/react` ради этой задачи — новая dev-зависимость, требует
явного одобрения пользователя (AGENTS.md §1) и в этом плане не запрашивается.
Реалистичная стратегия в границах текущего стека (без ссылки на
несуществующий precedent и без новых зависимостей — только приёмы, уже
применяемые в проекте сегодня, см. п.2 ниже):
1. Структурные/визуальные аспекты (цвет заливки, наличие/отсутствие
   `<title>`, отсутствие `TargetLoupe`-разметки при `dragging=null`) проверяются
   `renderToStaticMarkup`-снапшотом, как и сейчас.
2. Логика решения "что делать при pointerDown в readOnly" (выбрать ближайший
   выстрел и вызвать `onSelectShot`, либо ничего не делать при промахе, и
   не вызывать `onDragStart`) уже выражается через `findNearestShot`. В текущем
   `targetCanvas.render.test.tsx` такого precedent-а нет — существующие тесты
   только рендерят markup через `renderToStaticMarkup` и не вызывают
   обработчики напрямую. Для новой проверки: получить React-элемент через
   `React.createElement(TargetCanvas, props)` и достать `element.props.onPointerDown`
   из корневого `<svg>` элемента дерева, возвращённого вызовом `TargetCanvas(props)`
   как обычной функции компонента (без монтирования, без `renderToStaticMarkup`,
   без hooks-ограничений, т.к. сам компонент не использует состояние/эффекты для
   `onPointerDown`), затем вызвать этот обработчик с мок-объектом события
   (`{ clientX, clientY, pointerId: 1, preventDefault: () => {} } as unknown as React.PointerEvent`)
   и mock-функциями `onSelectShot`/`onDragStart` — без реального DOM и без новых
   зависимостей.
3. Полная интеграционная проверка реального drag/tap-цикла в браузере
   (например, что touch на телефоне действительно выбирает выстрел, а `<title>`
   показывается по hover) остаётся ручной/визуальной проверкой в ревью —
   это зафиксировано в acceptance criteria (§6) и как риск в §7.

Кейсы `renderToStaticMarkup`-части:
- `readOnly=true` рендерится без обработчиков создания (проверка через
  структурный снапшот markup — наличие `<svg>`/маркеров, отсутствие
  `TargetLoupe`-контейнера при отсутствии drag);
- маркер с `commentedShotIds` содержащим его id → залит `#3B82F6`;
- маркер без комментария → залит `black` (текущий default);
- `<title>` присутствует и содержит переданный текст для выстрела с
  `shotTooltip`, отсутствует для выстрела без него;
- маркер с `shotLabels` содержит переданное число в качестве подписи
  (globalNumber, не shotNumber).

Кейсы через прямой вызов `handlePointerDown`:
- pointerDown на выстреле в readOnly вызывает `onSelectShot` с правильным id и не
  вызывает `onDragStart`;
- pointerDown мимо выстрелов в readOnly не вызывает ни `onSelectShot`, ни `onDragStart`.

### 4.5. `src/screens/AllShotsScreen.tsx` (новый)

Копирует структуру `TrainingScreen`, но:
- Props: `{ athlete: AthleteRecord; onBack: () => void }`. **Решение после oracle

  `commentedShotIds = new Set(entries.filter(e => e.hasComment).map(e => e.shot.id))`,
  `tooltipByShotId = Map<shotId, commentText>`, `globalNumberByShotId = Map<shotId, number>`.

  `TrainingScreen`), либо `–`, если выстрелов нет вовсе. Формат фиксирован:
  номер — `globalNumber` (не per-training `shotNumber`), разделитель
  ` • `, затем ISSF-оценка в том же виде, что и `displayScore` в
  `TrainingScreen` (например `10.3`; для промаха — `shot.score === 0` — текущая
  конвенция `displayScore` даёт `'0.0'`, а не `'M'`; итоговый формат для
  промаха — `№{globalNumber} • 0.0`, например `№5 • 0.0`).
- Тулбар: только zoom-кнопка (переиспользует `ZOOM_MODES`/`ZOOM_LABELS`

  **решение: продублировать локально** — выносить в общий хук не входит в
  минимальный объём задачи и не запрошено.
- Без drag props — `TargetCanvas` вызывается с `readOnly`, `dragging={null}`,
  без `onDragStart/onDragMove/onDragEnd/onDragCancel`.
- Без кнопок «Отменить последний», «Добавить замечание», «Новая тренировка».

## 6. Тесты и acceptance criteria

Команда проверки: `npx vitest run` (должно остаться зелёным на всём
существующем наборе тестов + новые; конкретное число тестов в AGENTS.md/планах
не фиксируется — оно меняется с каждым PR и не является критерием приёмки;
единственное требование — 0 failed/0 skipped в итоговом отчёте `vitest run`),
опционально `npm run build` (проверка типов из-за новых optional props в `TargetCanvas`).

Acceptance criteria:
1. На экране тренировок спортсмена рядом с «Замечания» есть кнопка «Все
   выстрелы»; клик открывает новый экран для текущего спортсмена; на узком
   экране обе кнопки остаются полностью видимы и нажимаемы (перенос на
   вторую строку допустим, горизонтальное обрезание — нет), см. §4.7.
2. Экран показывает мишень со всеми `committed`-выстрелами спортсмена из
   всех его тренировок, координаты — исходные `x/y` без пересчёта.
3. Номера, используемые для выстрелов на этом экране, — это `globalNumber`:
   сквозные 1..N в хронологическом порядке тренировок, не равны per-training
   `shotNumber` при наличии >1 тренировки. `shotNumber` в `ShotRecord` при этом не
   изменяется и не переписывается нигде в `allShotsRepo`. В нижней панели
   `globalNumber` показывается полностью без ограничения; на самом маркере число
   рендерится только для `globalNumber` в диапазоне 1..99 (см. §3.3.1); для
   `globalNumber >= 100` маркер без числовой подписи — это ожидаемое поведение, не
   баг.
4. Выстрелы, у которых есть хотя бы один комментарий, залиты синим
   (`#3B82F6`); остальные — чёрным.
5. Клик по маркеру выделяет выстрел (эмфаз-размер) и внизу экрана
   показывается строго в формате `№{globalNumber} • {score}` (например
   `№12 • 10.3`, для промаха — `№5 • 0.0`) — см. §4.5.
6. Наведение (hover, desktop) на выстрел с комментарием показывает текст
   комментария через нативный `<title>` (автоматически проверяется через
   markup-снапшот, тап-сценарий на touch — ручная проверка, см. §7).
7. Zoom-кнопка переключает full/7-10/9-10 так же, как в `TrainingScreen`, и
   сохраняет режим в `targetZoomMode` (виден при повторном входе).
8. В этом экране невозможно создать новый выстрел или переместить
   существующий (`readOnly` блокирует `onDragStart` для пустого места и не
   даёт drag-перемещение уже стоящего маркера); подтверждается юнит-тестами
   прямого вызова `handlePointerDown` из §4.4, полная проверка реального touch/mouse
   цикла — ручная, см. §7.
9. На экране нет UI-фильтров (по дате/тренировке/оценке и т.п.).
10. `npx vitest run` зелёный (0 failed) на всём наборе, включая новые файлы
    `src/domain/allShotsRepo.test.ts` и
    `src/components/targetCanvasReadOnly.test.tsx`.

## 7. Риски / открытые вопросы

- Нативный `<title>` tooltip на touch-устройствах (основной формдактор
  тренера — телефон) может не открываться по тапу без hover-эмуляции
  браузера; если это окажется неприемлемым в ревью — потребуется отдельное
  решение (например, показ текста комментария в нижней панели при
  выделении выстрела) — выходит за рамки текущего плана, фиксируется как
  открытый вопрос для реализации.
- Полная автоматическая проверка «readOnly блокирует pointer-based
  создание/перемещение» ограничена возможностями текущего тестового
  стека (`vitest` без DOM-окружения, без `@testing-library/*`, см. §4.4):
  реальный `PointerEvent`/`pointercapture`-цикл браузера покрывается прямым
  юнит-вызовом `handlePointerDown` с мок-объектом события, а не полной
  интеграцией через `renderToStaticMarkup`; часть критерия 8 (реальный
  tap/drag на touch-устройстве) остаётся ручной проверкой в браузере/эмуляторе.
  Добавление `jsdom`/`happy-dom` + `@testing-library/react` для полной автоматизации
  — отдельное решение вне этого плана, требует явного одобрения новой
dev-зависимости (AGENTS.md §1).
- При множестве тренировок с очень большим количеством выстрелов
  (сотни/тысячи) плотность маркеров на одной мишени может ухудшить
  читаемость — вне рамок задачи (нет фильтров по требованию), фиксируется
  как известное ограничение, не требующее решения сейчас.
- Две кнопки («Замечания» + «Все выстрелы») в шапке `TrainingsScreen` на
  узких экранах могут переполнить горизонтальное пространство шапки рядом с
  именем спортсмена; минимальное исправление (`flex-wrap`) описано в §4.7;
  требует ручной проверки на узком вьюпорте, автотесты её не покрывают.
