# PLAN-DIARY-FOLD — свёртывание записей Дневника

Статус: planned (по рекомендациям Oracle, ожидает согласования пользователя
перед реализацией). Код не создаётся в рамках этого плана.

## 1. Проблема

`RemarksScreen` («Дневник») показывает все тренировки/упражнения и всё
содержимое каждой записи (общее замечание, серии ПП-3, замечания к
выстрелам) целиком и одновременно. По мере роста истории список становится
длинным и трудным для навигации: тренер должен пролистывать полностью
раскрытые старые записи, чтобы найти нужную свежую.

Нужна возможность свернуть/развернуть запись верхнего уровня (тренировка/
упражнение) и — внутри неё — каждую серию ПП-3 (со своей группой
выстрелов), без потери текущего поведения (клики по замечаниям, мете,
удаление, редактирование — не меняются).

## 2. Область (scope)

Два уровня складывания:

1. **Тренировка/упражнение** (`entry.training.id`) — сворачивает всё
   содержимое записи: общее замечание, список серий ПП-3 (или список
   shot-замечаний вне ПП-3).
2. **Серия ПП-3** (`training.id` + `row.index`) — сворачивает содержимое
   одной серии: её собственное замечание серии и вложенный список
   shot-замечаний этой серии. Заголовок серии (`Серия N · X выстрелов ·
   результат`) остаётся видимым всегда, независимо от состояния свёртки.

**Явно вне scope:** folding отдельных shot-замечаний (per-remark folding).
Каждое замечание к выстрелу продолжает отображаться целиком (текст, мета,
✎/✕), как сейчас — сворачивается только группа, в которую оно входит.

`TrainingRemarksScreen` (Дневник конкретной тренировки/серии) в этой
версии не получает folding — он уже показывает материал в узком scope
(одна тренировка или одна серия), список там короче. Если после внедрения
в `RemarksScreen` понадобится то же в `TrainingRemarksScreen`, это отдельная
задача с отдельным согласованием.

**Массовые действия «Свернуть все» / «Развернуть все»** входят в тот же
scope — только на экране `RemarksScreen`. Область действия обеих кнопок —
**все видимые в текущий момент записи этого экрана**: все тренировки/
упражнения текущего отфильтрованного списка `entries` и все вложенные серии
ПП-3 внутри них (в т.ч. серии внутри тренировок, которые до нажатия были
свёрнуты — массовое действие разворачивает/сворачивает их тоже, а не только
видимые в данный момент раскрытые). Кнопки не затрагивают
`TrainingRemarksScreen` и не меняют scope, описанный выше.

## 3. Модель состояния

### 3.1 Где живёт fold state

Fold state — это UI-навигационный контекст экрана «Дневник», не хранится в
IndexedDB (сворачивание — не доменные данные, не должно попадать в backup).
Он живёт **в записи навигационного стека `App.tsx`** для экрана `remarks`,
обновляется через `replaceTop`, аналогично тому, как `TrainingScreen`
сохраняет `restoreSeriesView` в своей записи стека (см. `AGENTS.md`/App.tsx
и `PLAN-DIARY-IA.md` §про conventions навигации). Смысл: если тренер уходит
с экрана «Дневник» вперёд (например, открыть замечание к выстрелу или
общий редактор) и возвращается назад, свёрнутые/развёрнутые записи должны
остаться как были — а не сброситься к дефолтам при повторном монтировании
`RemarksScreen`.

Изменение типа `Screen` в `App.tsx` (расширение варианта `'remarks'`):

```ts
| {
    name: 'remarks';
    athlete: AthleteRecord;
    /** Fold state per top-level diary entry (trainingId). Missing key = default (see §4). */
    foldedTrainings?: Record<string, boolean>;
    /** Fold state per ПП-3 series, keyed by `${trainingId}:${seriesIndex}`. Missing key = default. */
    foldedSeries?: Record<string, boolean>;
  }
```

`RemarksScreen` получает эти два поля как props (не собственный
`useState`) и мутирует их наружу через новые callback-пропсы
`onToggleTrainingFold(trainingId)` / `onToggleSeriesFold(trainingId,
seriesIndex)`, которые в `App.tsx` реализуются как `replaceTop` с
переключённым булевым значением по ключу.

Массовые кнопки используют тот же канал: `onCollapseAll()` / `onExpandAll()`
— тоже реализуются в `App.tsx` через `replaceTop`, но заменяют сразу оба
словаря (`foldedTrainings`, `foldedSeries`) целиком новыми объектами,
построенными из **текущего отрендеренного списка** `entries`/`pp3Series`
(переданного из `RemarksScreen` в вызов callback-а как аргумент, аналогично
тому, как уже вычисляются дефолты в §5): каждому видимому `training.id` и
каждому `seriesFoldKey(training.id, row.index)` присваивается `true`
(свернуть все) или `false` (развернуть все). Ключи записей, не входящих в
текущий видимый список (например, отфильтрованных или ещё не загруженных),
не создаются и не трогаются — массовое действие не должно писать в словарь
стека то, что тренер не видел на экране в момент нажатия.

`true` в записи словаря значит «свёрнуто», `false` — «явно развёрнуто
пользователем» (переопределяет дефолт), отсутствие ключа — «дефолт по
правилам §4» вычисляется чисто из данных записи при каждом рендере.

### 3.2 Почему не React state внутри RemarksScreen

Если fold state — обычный `useState` внутри `RemarksScreen`, он теряется
при каждом размонтировании/повторном монтировании экрана (уход на другой
экран стека и возврат — стандартный сценарий: открыть замечание к
выстрелу → назад). Хранение в стеке навигации `App.tsx` — тот же паттерн,
что уже используется для `restoreSeriesView` в `training`, и не требует
новых слоёв персистентности.

## 4. Дефолты (какие записи развёрнуты изначально)

Правила дефолта — чистая функция от данных записи (`entry`/`row`), без
знания истории кликов пользователя. Как только пользователь явно
переключил fold конкретной записи, явный выбор (`true`/`false` в словаре
стека) имеет приоритет над дефолтом.

- **Тренировка/упражнение развёрнута по умолчанию**, если хотя бы одно:
  - `training.completedAt === null` (тренировка ещё не завершена — самая
    актуальная, обычно самая свежая);
  - у записи есть `generalComment !== null`;
  - у записи есть хотя бы одно замечание к выстрелу (`shotComments.length
    > 0`) или хотя бы одна серия ПП-3 с непустым `seriesComment` или
    `shotComments`.
  - **иначе свёрнута** (старая пустая запись без единого замечания — только
    факт тренировки и результат).
- **Серия ПП-3 развёрнута по умолчанию**, если хотя бы одно:
  - `row.seriesComment !== null`;
  - `row.shotComments.length > 0`.
  - **иначе свёрнута** (серия без единого замечания — только заголовок с
    результатом).

Это соответствует принципу «новые/с комментариями раскрыты, старые/пустые
свёрнуты» из формулировки задачи: «новое» здесь операционализировано как
`completedAt === null` (продолжающаяся тренировка), поскольку `RemarksScreen`
не имеет отдельного понятия «свежести» — список уже сортирован по
`startedAt` по убыванию, и первая запись в списке физически самая новая
независимо от дефолта раскрытия. Для серий ПП-3 нет отдельного признака
«новизны», кроме наличия комментариев — используется только правило про
комментарии.

## 5. Чистая логика (`src/screens/diaryFold.ts`)

Новый модуль без React и без I/O (как `scoring.ts`/`transform.ts` —
принцип чистоты сохраняется и для UI-хелперов, где это возможно), тестируем
изолированно. Экспортирует:

```ts
export function seriesFoldKey(trainingId: string, seriesIndex: number): string;
// `${trainingId}:${seriesIndex}` — используется и как ключ словаря состояния,
// и как React key вложенного списка (см. §7 «стабильные ключи»).

export function defaultTrainingFolded(entry: {
  completedAt: string | null;
  hasGeneralComment: boolean;
  hasAnySeriesOrShotComment: boolean;
}): boolean;

export function defaultSeriesFolded(row: {
  hasSeriesComment: boolean;
  hasShotComments: boolean;
}): boolean;

export function isTrainingFolded(
  foldedTrainings: Record<string, boolean> | undefined,
  trainingId: string,
  defaultFolded: boolean,
): boolean;
// explicit value in the dict wins; otherwise defaultFolded.

export function isSeriesFolded(
  foldedSeries: Record<string, boolean> | undefined,
  trainingId: string,
  seriesIndex: number,
  defaultFolded: boolean,
): boolean;
```

`RemarksScreen` вызывает `defaultTrainingFolded`/`defaultSeriesFolded` при
построении списка `entries`/`pp3Series` (там же, где уже вычисляются
`resultLabel` и другие производные поля) и передаёт результат в
`isTrainingFolded`/`isSeriesFolded` для итогового булева при рендере.

## 5.1 Массовые действия — чистая логика

В `diaryFold.ts` добавляются два экспорта, используемые `RemarksScreen`
для построения аргументов `onCollapseAll`/`onExpandAll`:

```ts
export function collapseAllFoldState(entries: readonly {
  trainingId: string;
  seriesIndexes: readonly number[];
}[]): { foldedTrainings: Record<string, boolean>; foldedSeries: Record<string, boolean> };
// Каждой видимой записи и её видимым сериям присваивает true.

export function expandAllFoldState(entries: readonly {
  trainingId: string;
  seriesIndexes: readonly number[];
}[]): { foldedTrainings: Record<string, boolean>; foldedSeries: Record<string, boolean> };
// Каждой видимой записи и её видимым сериям присваивает false.
```

Обе функции чистые, не читают и не изменяют состояние стека сами — только
превращают текущий видимый список записей в готовые словари, которые
`RemarksScreen` передает наружу через `onCollapseAll(result)` /
`onExpandAll(result)`, а `App.tsx` кладёт в `replaceTop` без дополнительной
логики.

## 6. UI: chevron-кнопки и conditional render

### 6.1 Кнопка-шеврон (sibling, не обёртка)

Для каждого сворачиваемого узла (заголовок тренировки и заголовок серии)
добавляется отдельная кнопка-шеврон **рядом** с существующей кнопкой
заголовка (`s.diaryType` для тренировки, `s.pp3SeriesRow` для серии), а не
вместо неё и не как обёртка вокруг всего заголовка — существующие клики
(`onSelectTraining`, `onOpenSeriesDiary`) продолжают открывать целевой
экран, а клик по шеврону только переключает fold, без навигации:

```tsx
<button
  type="button"
  className={s.foldToggle}
  aria-expanded={!folded}
  aria-controls={contentId}
  aria-label={folded ? 'Развернуть запись' : 'Свернуть запись'}
  onClick={() => onToggleTrainingFold(entry.training.id)}
>
  {folded ? '▶' : '▼'}
</button>
```

- `aria-expanded` — фактическое состояние, обязательно синхронизировано с
  тем, что реально отрендерено (см. 6.2).
- `aria-controls` ссылается на `id` контейнера содержимого записи (нужен
  стабильный `id`, например `diary-training-${training.id}` /
  `diary-series-${trainingId}-${seriesIndex}`).
- `aria-label` — текстовая альтернатива для screen reader, т.к. глиф ▶/▼
  сам по себе не озвучивается осмысленно.
- Кнопка — фокусируемый интерактивный элемент со своим hit-target (не
  меньше существующих кнопок в этом экране, см. `tokens.css` для размеров
  тап-таргетов), не полагается только на цвет/иконку.
- Заголовок серии/тренировки и шеврон — соседние элементы одного flex-ряда
  (`s.diaryEntryHeader` / новый ряд для серии), не вложенность
  кнопка-в-кнопке.

### 6.2 Conditional render, без CSS-скрытия и анимации высоты

Свёрнутое содержимое не рендерится в DOM вовсе (`folded ? null :
<...content...>`), а не скрывается через `display:none`/`max-height`/
CSS-анимацию. Это совпадает с уже принятым в этом репозитории подходом
"conditional render без hidden-состояний" и убирает необходимость
анимаций раскрытия/сворачивания (явно исключены заданием). Заголовок
записи (дата, тип, результат / номер серии, счёт) всегда виден независимо
от fold — сворачивается только тело (замечания, вложенные списки).

### 6.3 Затронутая разметка (`RemarksScreen.tsx`)

- `entry.generalComment`/`RemarkRowEmpty` для общего замечания — рендерятся
  только если `!isTrainingFolded(...)`.
  зависят от training fold.
- `entry.pp3Series` список (`<ul className={s.pp3SeriesList}>`) — сам список
  серий рендерится, только если тренировка развёрнута (иначе он невидим
  вместе с остальным телом записи); заголовок каждой серии
  (`s.pp3SeriesRow`) рендерится всегда внутри развёрнутой тренировки, а
  вложенные `seriesComment`/`RemarkRowEmpty`/`shotComments` этой серии — по
  своему собственному `isSeriesFolded(...)`.
- `entry.shotComments` (не-ПП-3 ветка) рендерится только если тренировка
  развёрнута.

## 6.4 Кнопки «Свернуть все» / «Развернуть все»

- Располагаются один раз над списком `entries` (тулбар экрана, рядом с
  существующими элементами управления `RemarksScreen`, если такие есть;
  иначе — новая строка непосредственно над сиском).
- Каждая — обычная кнопка `type="button"`, не переключатель/чекбокс: клик по
  «Свернуть все» всегда переводит все видимые записи и их серии в `true`,
  клик по «Развернуть все» — всегда в `false`, независимо от того, что было
  до этого (смешанное состояние экрана не имеет отдельной третьей кнопки).
- `aria-label`/видимый текст — буквально «Свернуть все» и «Развернуть все»
  (не иконки без текста, в отличие от per-record шеврона в §6.1 — здесь текст
  обязателен, т.к. действие затрагивает весь список и должно быть однозначно
  понятно без визуального сканирования).
- Клик по любой из кнопок **не вызывает навигацию** — не должны срабатывать
  `onSelectTraining`, `onOpenSeriesDiary` или любой другой navigation-пропс;
  единственный эффект — `replaceTop` с новым fold state текущей записи стека
  (см. §5.1, §3.1).
- Клик по этим кнопкам **не ломает индивидуальный toggle**: после массового
  действия каждая отдельная запись/серия продолжает переключаться своим
  шевроном (§6.1) независимо от остальных — массовое действие просто
  один раз заполняет словарь явными значениями, дальше это обычные explicit
  overrides, как описано в §4.
- **Пустой дневник** (список `entries` пуст, ветка «Нет замечаний» из §10) —
  кнопки не рендерятся вовсе (нет смысла сворацивать пустой список); либо,
  если рендерятся, — задизейблены (`disabled`) без падения в клике. Выбор
  между «не рендерить» и «disabled» — на реализацию, при условии, что клик
  по кнопке в пустом состоянии не может выбросить ошибку и не создаёт записей
  в словарях стека.
- **Loading-состояние** (данные ещё не загружены, `entries` недоступны) —
  кнопки либо не рендерятся, либо задизейблены; в любом случае не вызывают
  `onCollapseAll`/`onExpandAll` с неполным/undefined списком.
- **Legacy/standalone пути открытия `RemarksScreen`** (см. §11 про
  обратную совестимость `push({ name: 'remarks', athlete })` без новых
  полей) — кнопки работают идентично во всех путях открытия экрана, т.к.
  зависят только от текущего `entries`, а не от истории навигации, которой
  экран был открыт; отсутствие `foldedTrainings`/`foldedSeries` в старой
  записи стека не мешает первому нажатию — `replaceTop` создаёт оба словаря
  с нуля.

## 7. Стабильные ключи

- Ключ записи тренировки в React-списке — `entry.training.id` (уже
  используется, не меняется).
- Ключ записи серии — `row.index` уже используется как React `key` внутри
  `entry.pp3Series.map`; для fold state дополнительно вводится составной
  строковый ключ `seriesFoldKey(training.id, row.index)`, т.к. `row.index`
  один и тот же для разных тренировок (номер серии внутри одного
  упражнения — не глобально уникален) и не может быть ключом
  общего словаря `foldedSeries` в `App.tsx`.
- Ключи словарей `foldedTrainings`/`foldedSeries` в состоянии стека не
  зависят от порядка/индекса в текущем отрендеренном списке — только от
  доменных id, поэтому re-sort/refetch (`load()` при возврате на экран)
  не путает fold state с чужими записями.

## 9. Критерии приёмки

1. При первом открытии «Дневника» после запуска приложения (пустой fold
   state в стеке) отображаются дефолты по правилам §4: незавершённые
   тренировки, тренировки/серии с любым замечанием — развёрнуты; полностью
   пустые старые тренировки/серии без замечаний — свёрнуты.
2. Клик по шеврону тренировки переключает видимость тела записи
   (замечание/серии/shot-замечания), не запускает навигацию
   (`onSelectTraining` не вызывается).
3. Клик по шеврону серии переключает видимость только тела этой серии
   (её `seriesComment` + вложенные `shotComments`), заголовок серии и
   остальные серии этой же тренировки не меняются.
4. Explicit toggle пользователя переопределяет дефолт: развернув
   изначально свёрнутую пустую запись, а затем свернув изначально
   развёрнутую запись с комментарием — оба состояния сохраняются как
   заданные явно.
5. Fold state переживает навигацию «вперёд-назад»: открыть замечание к
   выстрелу или общий редактор из развёрнутой/свёрнутой записи и вернуться
   назад — состояние (в т.ч. пользовательские переопределения) не
   сбрасывается и не пересчитывается из дефолтов повторно.
6. Fold state не появляется в backup/restore (`backupService`) и не
   создаёт новых записей/полей в IndexedDB.
7. Свёрнутое содержимое отсутствует в DOM (`renderToStaticMarkup`/DOM
   query для теста не находит текст свёрнутого замечания), а не скрыто
   CSS-классом — проверяется тестом на конкретной свёрнутой записи.
8. Кнопки-шевроны имеют `aria-expanded`, `aria-controls` (указывающий на
   существующий `id` контейнера тела) и текстовый `aria-label`,
   синхронизированные с фактическим состоянием рендера.
9. Существующее поведение не регрессирует: клики по мете shot-замечания
   (переход к выстрелу на мишени), редактирование/удаление любого типа
   замечания, кнопки «+ Добавить…» — работают идентично текущему при
   развёрнутом состоянии записи/серии.
10. `npx vitest run` зелёный, включая новые тесты для `diaryFold.ts` и
    как минимум один render-тест `RemarksScreen`, покрывающий сценарии
    2–3 и 7.
11. Клик по «Свернуть все» сворачивает все видимые записи текущего списка
    `entries` и все их серии ПП-3 (в т.ч. те серии, что были уже свёрнуты, —
    результат идемпотентен), не запускает никакую навигацию.
12. Клик по «Развернуть все» разворачивает все видимые записи и их серии,
    не запускает навигацию.
13. После массового действия индивидуальный шеврон отдельной записи/серии
    продолжает работать как обычный toggle (можно свернуть одну запись сразу
    после «Развернуть все», и это не откатывает остальные записи).
14. На пустом дневнике (ветка «Нет замечаний») клик/отсутствие кнопок не
    приводит к ошибке рендера и не создаёт записей в `foldedTrainings`/
    `foldedSeries`.
15. В loading-состоянии кнопки либо отсутствуют, либо не вызывают
    `onCollapseAll`/`onExpandAll` до того, как `entries` загружены.
16. Поведение кнопок идентично во всех путях открытия `RemarksScreen`,
    включая legacy/standalone `push({ name: 'remarks', athlete })` без
    предзаполненных `foldedTrainings`/`foldedSeries` в записи стека.

## 10. Edge cases

- **Тренировка без единой серии ПП-3 и без единого shot-замечания, но
  с общим замечанием** — тело развёрнуто по правилу §4 (generalComment
  присутствует), даже если тренировка давно завершена.
- **Тренировка режима `pp3` с сериями, где часть серий пуста, а часть — с
  комментариями** — fold применяется к каждой серии независимо; пустая
  серия внутри развёрнутой тренировки по умолчанию свёрнута сама по себе.
- **Серия без единого выстрела (`committedCount === 0`) и без
  `seriesComment`** — фильтруется на уровне текущей логики
  (`.filter(row => row.committedCount > 0 || ...)` в `RemarksScreen.tsx`)
  раньше, чем дойдёт до fold — эта фильтрация не меняется, fold применяется
  только к уже прошедшим фильтр строкам.
- **Явное переопределение записи, которая перестала существовать после
  удаления** (например, тренер удалил все замечания серии, свернув её
  вручную ранее) — ключ в словаре стека остаётся, но безвреден: при
  следующем рендере записи с этим id/индексом может не быть вовсе (после
  фильтрации), тогда ключ просто не используется; специальной очистки
  словаря не требуется.
- **Переключение fold во время открытого модального подтверждения
  удаления** (`confirmDelete`/`confirmDeleteGeneral`/`confirmDeleteSeries`)
  — шеврон недоступен для клика под открытым модалом (как и остальной
  экран), это уже обеспечивается `Modal` (см. текущее поведение), fold
  логика не добавляет отдельной защиты.
- **Пустой список `entries` целиком** (пункт «Нет замечаний») — fold state
  не применяется, ветка рендера не изменяется.
- **Быстрое повторное открытие/закрытие одного и того же шеврона** — чисто
  клиентское переключение булева значения в стеке, без обращения к
  IndexedDB, не может создать race с `load()`/эпохой данных.
- **`row.index` совпадает у серий разных тренировок** — уже разобрано в
  §7: составной ключ `seriesFoldKey` предотвращает коллизию в словаре
  `foldedSeries`.

## 11. Риски

- Расширение варианта `'remarks'` в `Screen` — единственное изменение вне
  `RemarksScreen`/`diaryFold.ts`; нужно аккуратно сохранить обратную
  совместимость мест, которые уже создают `{ name: 'remarks', athlete }`
  без новых полей (`push`/`reset` из `AthletesScreen`/`TrainingsScreen`/
  `TrainingRemarksScreen` — поля опциональны, значит старые вызовы
  остаются валидны).
- Если в будущем понадобится folding в `TrainingRemarksScreen`, схему
  ключей (`seriesFoldKey`) и модуль `diaryFold.ts` можно переиспользовать
  без переписывания — учтено намеренно, но реализация для этого экрана
  вне scope текущего плана.

## 12. Открытые вопросы к согласованию перед реализацией

Нет — все пункты, поднятые в постановке задачи (fold state в стеке через
`replaceTop`, два уровня, per-remark вне scope, sibling chevron с
accessibility, conditional render без CSS/анимации, чистый
`diaryFold.ts`, стабильные ключи, дефолты) закрыты выше. План готов к
review (`reviewer`)/оценке пользователем перед созданием задачи на
`worker` для реализации.
