# План разработки приложения тренера для 10 м пневматического пистолета

## 1. Цель проекта

Создать простое мобильное PWA-приложение для тренера, который во время тренировки стоит за спортсменом и видит на мониторе электронной мишени точное положение каждого выстрела.

Тренер вручную переносит положение выстрела на экран приложения:

1. тапает примерно в место попадания;
2. перемещает маркер пальцем;
3. во время перемещения сразу видит изменяющееся значение выстрела;
4. отпускает маркер;
5. при необходимости снова тапает по этому выстрелу и корректирует его любое количество раз.

Приложение хранит данные локально на устройстве тренера. Сервер используется только для доставки приложения и не хранит персональные данные спортсменов.


В MVP достаточно имени.

## 4.2. Training

Тренировка конкретного спортсмена.

```text
id
athleteId
startedAt
updatedAt
completedAt / null
nextShotNumber
```

`nextShotNumber` (integer, начальное значение 1) — возрастающий счётчик следующего номера выстрела. Не уменьшается при повторном открытии завершённой тренировки — номер, занятый существующим выстрелом, не может появиться повторно. При отмене ещё не зафиксированного draft-выстрела (`pointercancel`) и при Undo последнего committed-выстрела (раздел 12) счётчик пересчитывается до `max(shotNumber оставшихся выстрелов) + 1` в той же транзакции, что и удаление, но никогда не опускается ниже номера, занятого существующим выстрелом.

Тренировка представляет собой **одну последовательность из N выстрелов**.

Количество выстрелов заранее не задаётся.

Тренировка может содержать:

* 10 выстрелов;
* 20;
* 37;
* 100 и т.д.

---

## 4.3. Shot

Базовая единица данных.

```text
id
trainingId
shotNumber
x
y
score
status
createdAt
updatedAt
```

`x` и `y` — **целые числа сотых миллиметра** (диапазон −;8000..8000, т.е. до ±80,00 мм). Начало координат — геометрический центр мишени, ось X вправо, ось Y вверх. UI отображает значения как `xh/100` мм.

Пример:

```text
x = -320   (÷100 = -3.20 мм)
y =  1245  (÷100 = 12.45 мм)
```

`score` — производный кэш от `(x, y)`, единственный источник истины — координаты. Хранится как **integer tenths** (109..10 и 0). Отдельное изменение `score` без обновления координат невозможно; запись `x`, `y`, `score` всегда выполняется в одной транзакции.

`status` — `'draft'` | `'committed'`. Draft-выстрелы не участвуют в агрегатах, не попадают в backup. При старте приложения все `draft`-выстрелы удаляются (см. раздел 18).

**Правило нумерации:**

При создании выстрела: `shotNumber = training.nextShotNumber`, затем `nextShotNumber` увеличивается на 1 в той же транзакции.

**Правило согласованности score:**

При изменении `SCORING_VERSION` (константа, хранится в `settings`) при старте приложения выполняется пересчёт `score` для всех выстрелов в одной транзакции. При restore `score` пересчитывается из координат, значения из файла игнорируются. При чтении `score` берётся из хранилища без пересчёта.

### Важное правило нумерации

`shotNumber` — порядковый номер события в тренировке.

Номера автоматически не перенумеровываются при удалении.

Например:

```text
1
2
3
4
5
6
```

если выстрел №5 удалён:

```text
1
2
3
4
6
```

Это сохраняет фактическую последовательность событий.

# 9. Ввод выстрела

## 9.0. Модель жеста

Обработка на уровне Pointer Events. Жест имеет два состояния:

* **draft** — координаты живут только в памяти;
* **committed** — координаты записаны в IndexedDB.

**Последовательность создания выстрела:**

На `pointerdown` в одной транзакции резервируется `shotNumber` (инкремент `nextShotNumber`) и создаётся запись Shot со `status = 'draft'`. Далее жест переходит в draft.

`pointermove` НЕ пишет в IndexedDB — обновляются только состояние в памяти и отображаемый score.

На `pointerup` финальные `x`, `y`, `score` + `status = 'committed'` записываются в одной транзакции.

На `pointercancel`: draft-запись удаляется в одной транзакции; если удалённый draft был выстрелом с наибольшим номером в тренировке, `nextShotNumber` пересчитывается как `max(shotNumber оставшихся выстрелов) + 1` (номер отменённого незакоммиченного выстрела переиспользуется). Счётчик никогда не опускается ниже номера, требуемого существующими выстрелами. Undo последнего committed-выстрела (раздел 12) пересчитывает `nextShotNumber` тем же способом и в той же транзакции, что и удаление выстрела, — повторные Undo не оставляют пропусков в нумерации.

**Редактирование существующего выстрела:**

На `pointerdown` запись не изменяется, исходные координаты сохраняются в памяти как `originalCoords`. Drag — только в памяти. На `pointerup` — одна транзакция обновления `x`, `y`, `score`, `updatedAt`. На `pointercancel` — записи в IndexedDB не выполняется, возврат к `originalCoords`.

**Правило выбора режима:**

На `pointerdown` вычисляется ближайший существующий маркер. Если расстояние до него в CSS px ≤ 24, жест трактуется как редактирование этого маркера; иначе создаётся новый выстрел. При нескольких маркерах в hit-radius выбирается ближайший; при равном расстоянии — с наибольшим `shotNumber`.

**Другие правила:**

Во время drag координаты клампируются на границу r = 80,0 мм. `pointerdown` вне области мишени игнорируется.

Обрабатывается только первый активный pointer; остальные касания игнорируются до `pointerup`/`pointercancel`.

Записи выстрела сериализуются: новая транзакция для того же выстрела не стартует до завершения предыдущей.

При ошибке записи на `pointerup`: показать сообщение (раздел 18), перечитать выстрел из IndexedDB, отобразить последнее успешно сохранённое положение.

## 9.1. Новый выстрел

Если тренер нажимает на свободное место мишени:

→ создаётся новый выстрел.

Например:

```text
Выстрел №17
```

Появляется маркер.

---

## 9.2. Drag

После появления маркера тренер перемещает его пальцем.

Во время `pointermove` приложение непрерывно:

1. получает координаты пальца;
2. переводит их в координаты мишени;
3. пересчитывает score;
4. немедленно обновляет score на экране.

То есть:

```text
9.6 → 9.7 → 9.8 → 9.9 → 10.0
```

без необходимости отпускать палец.

---

## 9.3. После отпускания

На `pointerup` финальные координаты и score фиксируются в IndexedDB одной транзакцией; выстрел остаётся редактируемым.

Отпускание **не делает выстрел неизменяемым**.

Это принципиальное UX-требование.

# 10. Повторное редактирование

Последний выстрел всегда остаётся редактируемым.

Например:

```text
tap
→ drag
→ 9.8
→ release
```

Тренер смотрит ещё раз на монитор:

> Нужно немного правее.

Он снова тапает по этому выстрелу:

```text
tap
→ drag
→ 9.9
→ release
```

Это можно повторять сколько угодно раз.

### Также редактируются старые выстрелы

Тап по существующему маркеру должен переводить его в режим редактирования.

Таким образом:

* tap по пустому месту → новый выстрел;
* tap по существующему выстрелу → редактирование;
* drag → изменение координат;
* score изменяется в реальном времени.

# 12. Undo

Undo отменяет только **последнее создание выстрела** и только пока, этот выстрел является последним в тренировке и не был отредактирован после создания.

Undo **не отменяет**: редактирование координат, удаление выстрела/спортсмена/тренировки, restore.

Состояние Undo хранится только в памяти; очищается при переключении спортсмена, выходе с экрана тренировки, завершении тренировки и перезапуске приложения.

Undo удаляет последний committed-выстрел и в той же транзакции пересчитывает `nextShotNumber` до `max(shotNumber оставшихся выстрелов) + 1` (никогда не ниже занятых номеров), чтобы повторные Undo не оставляли пропусков в нумерации (например 11, 12 вместо продолжения с 9, 10).

# 13. Завершение тренировки — УСТАРЕЛО

> Этот раздел описывает историческую модель с одной active-тренировкой, завершением и продолжением. Она больше не используется. Текущая модель: тренировки независимы, любую тренировку можно открыть и быстро переключать; кнопок «Завершить»/«Продолжить» нет. Единственное действие в списке — `X` с подтверждением удаления.

Кнопка:

**Завершить тренировку**

показывает подтверждение:

```text
Завершить тренировку?

37 выстрелов
Среднее 9.76

[Продолжить] [Завершить]
```

После завершения тренировка сохраняется в истории.

Она **не блокируется**:

> позже её можно снова открыть и продолжить.

## 13.1. Состояния тренировки

Тренировка имеет два состояния:

* **active** — `completedAt = null`;
* **completed** — `completedAt` задан.

У спортсмена может быть не более одной active-тренировки. Попытка создать новую при наличии active требует подтверждения и завершает текущую.

При быстром переключении спортсмена (раздел 6) открывается его active-тренировка; если её нет — экран выбора тренировки.

**Переходы жизненного цикла** (каждый атомарно в одной IndexedDB-транзакции над стораджем trainings):

* (**a**) создание новой при наличии active: завершить прежнюю + создать новую;
* (**б**) переход completed → active («Продолжить»): завершить другую active + сбросить `completedAt = null`;
* (**в**) завершение active: `completedAt = now`, `updatedAt = now`.

Внутри транзакции инвариант проверяется повторно: если обнаружена посторонняя active-тренировка, она завершается в той же транзакции. После коммита у спортсмена ровно одна active-тренировка.

При откате: состояние тренировок не меняется, UI остаётся на текущем экране, выводится сообщение (раздел 18). Приложение перечитывает состояние тренировок из IndexedDB и перерисовывает экран по фактическим данным.

# 14. Скоринг ISSF

Использовать актуальную геометрию 10 m Air Pistol из Rule Book 2026.

Для 10 м пневматического пистолета ISSF указывает диаметры:

```text
10 — 11.5 mm
9  — 27.5 mm
8  — 43.5 mm
7  — 59.5 mm
6  — 75.5 mm
5  — 91.5 mm
4  — 107.5 mm
3  — 123.5 mm
2  — 139.5 mm
1  — 155.5 mm

Inner ten — 5.0 mm
```

Допуски мишени в расчёте не применяются: используются номинальные размеры.

ISSF разрешает decimal scoring для электронных мишеней: scoring area одного полного кольца делится на десять равных decimal scoring rings, например от 10.0 до 10.9.

### Важное техническое требование

Не реализовывать scoring как приблизительную формулу «по расстоянию до центра» без проверки.

Нужно:

1. определить точную модель decimal scoring;
2. реализовать её отдельно от UI;
3. создать набор эталонных тестовых координат;
4. проверить переходы между 10.x, 9.x, 8.x и т.д.;
5. проверить граничные случаи.

Scoring должен быть отдельным чистым модулем:

```text
score(x, y) → decimal score
```

чтобы UI никак не зависел от конкретной реализации формулы.

## 14.1. Точная модель decimal scoring

**Геометрия** (диаметр пули 4,5 мм, радиус 2,25 мм):

* внутри кольца 10 (d от 0 до 5,75 мм): 10 decimal rings по w₁₀ = 0,575 мм;
* вне кольца 10 (d от 5,75 до 77,75 мм): 90 decimal rings по w = 0,8 мм.

**Алгоритм** (целочисленное сравнение, без sqrt/ceil):

```
1. Квантовать x, y до сотых мм (целые xh, yh)
2. xu = 10 * xh, yu = 10 * yh  (микрометры)
3. R2 = xu² + yu²

Границы в мкм:
  Rk = 2250 + 575*k,  k = 1..10  (внутри кольца 10)
  Rm = 8000 + 800*m,  m = 1..90  (вне кольца 10)

Результат:
  R2 <= 2250²               → tenths = 109  (10.9)
  R2 <= Rk²  (мин k=1..10)  → tenths = 109 - k
  R2 <= Rm²  (мин m=1..90)  → tenths = 100 - m
  R2 > 80000²               → tenths = 0   (промах)
```

Граница включается в лучшее значение (нестрогое сравнение `<=`).

**Диапазон**: 100 значений от 10.9 до 1.0 (шаг 0.1) + 0.0 (промах). Хранится как integer tenths (109..10, 0).

**Отображение**: всегда одна цифра после точки («9.8», «10.0», «0.0»).

**Inner ten** (радиус 2,5 мм): на decimal score не влияет, в MVP отдельно не подсчитывается.

**Порядок операций**: сначала квантование координат до сотых мм (half-up на входе экран → мишень), затем score вычисляется исключительно от квантованных координат.

**Эталонные тесты**: для каждой из 100 границ по две точки в целых мкм: точно на границе (ожидается лучшее значение) и на 10 мкм дальше (ожидается на 0.1 меньше). Дополнительно: (0,0) → 10.9; r = 80.01 мм → 0.0; симметрия по знакам x, y.

# 15. Анализ с AI

Функция доступна в `SettingsScreen` → секция «Анализ с AI».

### Возможности

# 16. Backup

Backup — обязательная функция MVP.

В приложении:

```text
Настройки

Данные

[ Сохранить резервную копию ]

[ Восстановить из резервной копии ]
```

### Сохранение

Создаётся **один файл со всеми данными приложения**:

```text
coach-backup-2026-08-18.json
```

Он содержит:

* всех спортсменов;
* все тренировки;
* все выстрелы;
* координаты;
* результаты;
* необходимые настройки.

Приложение не отправляет backup на сервер.

Пользователь сам выбирает, куда сохранить файл.

## 16.1. Схема backup-файла

Единственная поддерживаемая версия — `version = 1`. Предыдущих версий не существует, миграции backup в MVP отсутствуют.

Обязательные поля: `version`, `exportedAt` (ISO 8601 UTC), `athletes[]`, `trainings[]`, `shots[]`, `settings`. Дополнительные поля в объектах запрещены.

Типы: `id` — UUID v4; временные поля — ISO 8601 UTC; `x`, `y` — целые числа сотых мм; `score` — integer tenths; `shotNumber`, `nextShotNumber` — integer.

Формальная схема:

```text
athlete:  id, name, createdAt, updatedAt
training: id, athleteId, startedAt, updatedAt, completedAt|null, nextShotNumber
shot:     id, trainingId, shotNumber, x, y, score, status, createdAt, updatedAt
```

`SCORING_VERSION` включается в backup только как справочная информация; при восстановлении не используется. Служебные поля (`dataEpoch` и др.) в backup не переносятся.

## 16.2. Согласованность экспорта

Чтение `athletes`, `trainings`, `shots`, `settings` выполняется в одной IndexedDB readonly-транзакции. Формирование JSON происходит после её успешного завершения.

В экспорт включаются только `status = 'committed'` выстрелы.

Экспорт не стартует во время активного жеста ввода (9.0) и во время restore (ожидается сообщение «Дождитесь завершения текущей операции»).

Перед записью файла экспортированный набор проверяется теми же инвариантами, что и restore (правила 3–7 раздела 17 + доменные инварианты); при нарушении — «Не удалось создать резервную копию: обнаружено несогласованное состояние данных».

# 17. Restore

Пользователь выбирает backup-файл.

Перед восстановлением:

```text
Восстановить резервную копию?

Текущие данные будут заменены
данными из выбранной копии.

[Отмена] [Восстановить]
```

После восстановления приложение получает состояние из backup.

Backup должен быть самодостаточным: новый телефон → установить приложение → импортировать backup → получить всю историю.

### Правила валидации

Данные из файла полностью валидируются в памяти до какой-либо записи:

1. `version` = 1 (при `version > 1` — «Файл создан более новой версией приложения»; иначе — всеобщее сообщение);
2. JSON корректен;
3. все обязательные поля присутствуют и имеют верный тип;
4. ссылочная целостность: `training.athleteId` и `shot.trainingId` существуют;
5. дубликаты `id` отсутствуют;
6. `x`, `y` — целые в диапазоне -8000..8000, `x² + y² <= 8000²`;
7. `nextShotNumber > max(shotNumber)` выстрелов тренировки (1 при отсутствии выстрелов);
8. `shotNumber` внутри тренировки — целые, >= 1, уникальные;
9. не более одной active-тренировки у спортсмена — **УСТАРЕЛО**, несколько тренировок могут существовать одновременно;
10. временные поля согласованы: `createdAt <= updatedAt`, `startedAt <= completedAt`; все — валидные ISO 8601 UTC;
11. `name` — непустая строка, <= 100 символов;
12. `status` каждого shot = `'committed'`;
13. `settings` содержит только ключи из whitelist; неизвестные ключи делают файл невалидным.

Валидация выполняется полностью до старта записи; причина отказа пишется в консоль. Сообщение при невалидном файле: **«Файл резервной копии повреждён или несовместим. Данные не изменены.»**

### Атомарность и протокол restore

1. Клиент, выполняющий restore, отправляет `{ type: 'RESTORE_BEGIN' }` по `BroadcastChannel('coach-data')`;
2. все прочие клиенты отменяют активный жест (эквивалент pointercancel) и переходят в read-only режим;
3. выполняется валидация в памяти;
4. в одной readwrite-транзакции: стораджи очищаются, заполняются данными из файла, `SCORING_VERSION` заменяется текущей сборки, `score` пересчитывается из `(x, y)`, `dataEpoch = previousEpoch + 1`;
5. после коммита: `{ type: 'RESTORE_DONE', dataEpoch }`, все клиенты перезагружаются.

При откате: `{ type: 'RESTORE_ABORTED' }`, `dataEpoch` не меняется, клиенты выходят из read-only режима.

Устаревший клиент (не получивший `RESTORE_DONE`), при первой попытке мутации обнаружит расхождение `dataEpoch`, прерывает транзакцию (abort) и перезагружается.

# 18. Удаление

Разрешить удаление:

* спортсмена;
* тренировки;
* отдельного выстрела.

Удаление спортсмена и тренировки требует подтверждения.

Например:

```text
Удалить тренировку?

18.08.2026
37 выстрелов

Это действие нельзя отменить.

[Отмена] [Удалить]
```

Удаление не должно приводить к автоматической перенумерации оставшихся выстрелов.

**Каскадное удаление:**

Удаление спортсмена каскадно удаляет все его trainings и все shots этих trainings. Удаление training каскадно удаляет все её shots.

Всё каскадное удаление выполняется в одной IndexedDB readwrite-транзакции; при ошибке — откат целиком.

При ошибке записи или QuotaExceededError: **«Не удалось сохранить данные. Освободите место на устройстве и повторите.»** Состояние UI откатывается к последнему успешно сохранённому.

При старте приложения удаляются: (1) все Shot со `status = 'draft'`; (2) осиротевшие shots (без training) и trainings (без athlete). Удаление draft-выстрелов из (1) в той же транзакции пересчитывает `nextShotNumber` затронутых тренировок до `max(shotNumber оставшихся committed-выстрелов) + 1` — иначе счётчик остаётся завышенным после незакрытой сессии (например, приложение закрыто во время drag) и следующий выстрел получает номер с пропуском.

# 19. Хранение данных

Использовать IndexedDB.

Структура:

```text
athletes
trainings
shots
settings
```

**Единая система координат** — миллиметры мишени; начало — центр; ось X вправо, Y вверх. Нормализация происходит только в слое transform (раздел 20) и никогда не попадает в persistence или backup.

Хранимое представление `x`, `y` — **integer hundredths**: целое число сотых мм (диапазон -8000..8000). UI показывает `xh/100` мм. Нормалонь равнен 80,00 мм (r > 80,0 мм недопустимо; точки вне радиуса не сохраняются).

**Индексы** (`shots.trainingId`, `trainings.athleteId`) обязательны.

В `settings` хранятся:

* `SCORING_VERSION` — константа версии scoring-модуля;
* `dataEpoch` — integer (нач.зн. 1), увеличивается только при restore;
* `storagePersisted` — результат запроса `navigator.storage.persist()`;
* `lastBackupAt` — время последнего backup.

## 19.1. Транзакционные границы

Одной IndexedDB readwrite-транзакцией выполняются:

* (**a**) создание выстрела + `draft` + инкремент `nextShotNumber`;
* (**б**) обновление `x`, `y`, `score`, `status = 'committed'` выстрела;
* (**в**) каскадное удаление;
* (**г**) restore целиком;
* (**д**) переходы жизненного цикла тренировки (13.1);
* (**е**) экспорт backup — одна **readonly**-транзакция над `athletes`, `trainings`, `shots`, `settings`.

**Общее правило:** каждая readwrite-транзакция мутации (а-д) в начале читает `settings.dataEpoch` и сравнивает с epoch, загруженным клиентом. При расхождении: abort, сообщение «Данные восстановлены из резервной копии в другом окне. Приложение будет перезагружено», перезагрузка.

## 19.2. Устойчивость хранения

При создании первого спортсмена приложение однократно вызывает `navigator.storage.persist()`; результат сохраняется в `storagePersisted`.

При отказе или отсутствии API: работа не блокируется, но в «Настройки → Данные» показывается: «Браузер может удалить локальные данные при нехватке места. Регулярно сохраняйте резервную копию».

В «Настройки → Данные» показывать usage/quota из `navigator.storage.estimate()` и статус persistent storage.

Если с последнего backup прошло > 7 дней или добавлено > 200 выстрелов, при завершении тренировки показывается ненавязчивое напоминание (с кнопками «Сохранить» / «Позже»).

# 24. Работа без интернета

После первого открытия PWA должна кэшировать необходимые ресурсы.

В offline-режиме должны работать:

* список спортсменов;
* создание спортсмена;
* открытие тренировок;
* создание тренировок;
* ввод выстрелов;
* редактирование;
* scoring;
* история;
* backup;
* restore.

Приложение не должно зависеть от сетевого запроса при каждом выстреле.

## 24.1. Обновление приложения

Стратегия кэширования: precache всех сборочных ассетов с версионированными именами (хеш). Навигация всегда отдаёт `index.html` из кэша активной версии.

**Протокол обновления** (при подтверждении пользователя «Перезагрузить»):

1. страница отправляет waiting-worker сообщение `{ type: 'SKIP_WAITING' }`;
2. worker вызывает `self.skipWaiting()`;
3. страница ждёт событие `navigator.serviceWorker.controllerchange`;
4. после `controllerchange` — `location.reload()` ровно один раз.

Таймаут: если `controllerchange` не наступил за 5 сек, баннер остаётся с текстом: «Обновление не удалось применить. Закройте все вкладки приложения и откройте его снова».

Баннер обновления не показывается во время активного жеста ввода (9.0) и появляется только в состоянии waiting for shot (раздел 23).

## 24.2. Миграции IndexedDB

Версия схемы — числовая версия IndexedDB (нач. = 1). Миграции выполняются только вперёд, без удаления пользовательских данных.

**Staged-протокол миграции:**

1. `indexedDB.open(name)` без указания версии — читается фактическая версия;
2. если фактическая версия < целевой и миграция меняет формат данных — через то же соединение выполняется экспорт backup (16.2) и предлагается сохранить файл;
3. соединение закрывается;
4. `indexedDB.open(name, targetVersion)` с `onupgradeneeded`.

Каждое соединение регистрирует `onversionchange` и немедленно закрывается при его получении. Если `blocked` получен при `open` с новой версией — сообщение «Закройте другие окна приложения, чтобы завершить обновление данных».

Если фактическая версия > целевой (возврат к старым ассетам) — блокирующий экран «Данные созданы более новой версией приложения» + сохранение backup (без записей). Понижение версии запрещено.

При ошибке upgrade-транзакции: блокирующий экран «Не удалось обновить формат данных. Сохраните резервную копию и переустановите приложение» + кнопка сохранения backup; запись недоступна.

Миграции выполняются в одной upgrade-транзакции без сетевых запросов и UI-обращений; каждая сопровождается тестом «База v.N → миграция → все записи сохранены».

# 25. Тестирование

Особое внимание уделить пяти группам тестов.

### Scoring

Проверить:

* центр;
* границы колец;
* переходы 10.x → 9.x;
* переходы 9.x → 8.x;
* отрицательные/положительные X/Y;
* симметричность относительно центра;
* эталонный набор 14.1 — 100 границ, две точки на границу и +0.01 мм от неё.

### Coordinate mapping

Одна и та же точка должна корректно отображаться на разных размерах экрана.

### Touch interaction

Проверить:

* tap;
* drag;
* повторный tap;
* повторное редактирование;
* быстрый drag;
* случайный tap;
* близко расположенные выстрелы.

### Persistence

После:

* закрытия браузера;
* перезагрузки;
* перехода offline;
* повторного открытия

данные не должны пропадать.

Дополнительно: принудительное закрытие приложения во время активного жеста → после повторного открытия ложный выстрел отсутствует, номера сохранённых выстрелов не изменились.

### Backup

Проверить полный цикл:

```text
создать спортсменов
→ создать тренировки
→ сделать выстрелы
→ отредактировать выстрел
→ backup
→ удалить данные
→ restore
→ сравнить состояние
```

Результат должен быть идентичен исходному (побайтовое сравнение повторного экспорта кроме `exportedAt`).

Дополнительно:

* restore негативных кейсов (дубликат `shotNumber`, `completedAt < startedAt`, нецелые `x`/`y`, неизвестный ключ settings, shot со `status='draft'`) — каждый файл отклоняется; проверка «две active-тренировки» **УСТАРЕЛА**;
* два клиента (Tab + Standalone): restore в одном — второй не может записать выстрел старого набора и перезагружается.

### Проверка production-сборки

В DevTools при полном прохождении сценария раздела 29: отсутствуют сетевые запросы к любым origin, кроме origin приложения; CSP-нарушения в консоли отсутствуют.

Ручная проверка полного цикла backup/restore на iOS 16.4+ (Safari) и Android Chrome 110+.

# 29. Критерий готовности MVP

MVP считается готовым, когда тренер может взять обычный телефон и выполнить следующий сценарий без каких-либо технических знаний:

```text
Открыть приложение
      ↓
Выбрать Иван Петров
      ↓
Создать тренировку
      ↓
Увидеть выстрел на мониторе электронной мишени
      ↓
Tap по мишени в приложении
      ↓
Передвинуть маркер
      ↓
В реальном времени увидеть, например, 9.8
      ↓
Отпустить
      ↓
При необходимости снова передвинуть этот же выстрел
      ↓
Сделать ещё 19 / 30 / 50 выстрелов
      ↓
Закрыть приложение
      ↓
Открыть снова
      ↓
Найти спортсмена
      ↓
Открыть тренировку
      ↓
Продолжить её
      ↓
Сохранить полный backup
```

Если этот сценарий работает **быстро, надёжно и без объяснения тренеру, куда нажимать**, основная задача MVP выполнена.

## 29.1. Измеримые критерии приёмки

* **Экран:** iPhone SE (375×667 CSS px) и Android 360 CSS px — мишень полностью без скролла в portrait.
* **Live scoring:** обновление score во время drag — не позже одного кадра после `pointermove`; 60 fps, без пропущенных кадров.
* **Запись выстрела:** IndexedDB ≤ 100 ms; UI не блокируется.
* **Объём тестовых данных:** 5 спортсменов, 20 тренировок, 2000 выстрелов; открытие тренировки с 100 выстрелами ≤ 300 ms.
* **Coordinate mapping:** цикл экран → мишень → экран — расхождение ≤ 1 CSS px.
* **Backup/restore:** цикл backup → очистка → restore → повторный экспорт — побайтово идентичны кроме `exportedAt`.
* **Offline:** после первой загрузки — авиарежим — полный сценарий раздела 29 без ошибок.

## 30. Ключевое архитектурное решение

Главное, что нужно не потерять при реализации:

> **Приложение не является системой учёта серий. Оно является локальным журналом последовательности выстрелов.**

Серия из 10, 20 или любого другого количества — это уже способ посмотреть на эту последовательность в будущем.

Каждый выстрел должен оставаться самостоятельным объектом с координатой и временем. Именно это позволит позже без переделки модели добавить анализ групп, произвольных диапазонов, динамику спортсмена и другие тренерские инструменты.

#### Шаг 1 — Scoring module (фундамент, без UI)

**Реализовать первым**: ошибка в scoring-алгоритме откатит всё остальное.

1. Модуль `scoring.ts`: функция `score(xh: number, yh: number): number` (integer tenths).
   - Входные данные: integer hundredths (−8000..8000).
   - Алгоритм: перевести в микрометры → вычислить `R2 = xu² + yu²` → табличное сравнение по границам (раздел 14.1).
   - Константа `SCORING_VERSION = 1`.
2. Тесты (раздел 25 «Scoring»):
   - 100 пар точек на границах (ровно на границе → лучшее; +0.01 мм → на 0.1 меньше).
   - `(0,0)` → 10.9; `r = 80.01 мм` → 0.0; симметрия по x/y.
3. **Проверка**: все тесты зелёные, модуль не импортирует ничего из UI.

#### Шаг 2 — IndexedDB persistence layer

1. Схема v1: стораджи `athletes`, `trainings`, `shots`, `settings`; индексы `shots.trainingId`, `trainings.athleteId`.
2. Реализовать staged-протокол открытия (раздел 24.2): `open()` без версии → проверка → `open(1)` с `onupgradeneeded`; `onversionchange` закрывает соединение.
3. Startup-очистка: удалить все `status='draft'` shots и осиротевшие записи.
4. `settings.dataEpoch = 1`, `settings.SCORING_VERSION = 1`.
5. **Транзакционные обёртки** для операций (a)–(д) из раздела 19.1; каждая начинает с проверки `dataEpoch`.
